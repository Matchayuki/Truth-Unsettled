# 《真理未决》微信小游戏

> THESIS / COUNTERTHESIS
> 一场关于公共命题的阵营推理桌游 · 4—8 人 · 隐藏阵营 · 公开表决

这是《真理未决》的微信原生小游戏版本。项目保留 `compileType: "game"`，使用 Canvas 2D 绘制，云端 `game` 云函数负责权威结算。创建房间的玩家也是普通玩家，没有主持人权限。

本版本重写了规则引擎与客户端界面：规则数据只有一份，云端与本地测试共用；客户端不再保存牌库副本。

### 与原版网页的差异

原版网页是“主持人裁决 + 电子桌”的形态；小游戏必须由系统自动主持，因此做了以下明确取舍：

1. **“计票后、公布结果前”的技能改成投票阶段内改票。**
   涉及柏拉图「洞穴寓言」、安萨里「确信」。小游戏的投票是同时秘密提交，在结算前改票与“计票后改票再公布”的结果等价。
2. **韩非「法不阿贵」改为令一件装备本议题失效。**
   原效果是“取消刚触发的装备效果”，需要中断任意装备触发；小游戏改为可操作、可预期的“指定装备失效”。
3. **休谟「因果怀疑」改为抵消一张指定自己的锦囊牌**（无需弃牌）。
4. **部分“可以”的防守效果默认发动。**
   佛珠、中道、单一实体、汉谟拉比法典、议题“善意”护佑等，在受到伤害时自动支付最合理的代价（弃 1 张牌等），避免每次伤害都弹窗。手牌为 0 时不发动。
5. **苏格拉底「反诘」、黑格尔「辩证扬弃」、安萨里「怀疑之路」可以在辩论阶段随时发动**，不要求轮到自己；其余主动技能仍按牌面时机校验。
6. **辩论阶段每名存活玩家各行动一次**，全部结束后进入投票；一回合内可以连续打出多张牌，但受同名上限约束。
7. **手牌数量公开。** 自动结算“手牌最多者”“手牌比你多”等效果需要比较；实体桌上手牌厚度本来也可见。
8. **投票提交后仍可改投**，直到全员提交或投票超时；被诘问 / 让步 / 修辞烟幕锁定的投票除外。

这些取舍都集中在规则引擎中，后续可以逐项改回更复杂的交互。

### 为什么客户端没有牌库数据

旧版本把 `cards.js` 复制到了 `js/` 和云函数两处，任何一次改牌都可能两端不一致。现在：

- 牌面由云端按玩家视角下发（`hand`、`equipment`、`agenda`）；
- 角色技能与可用性由云端计算后下发（`self.skills`）；
- 客户端只保留颜色、排版与交互逻辑。

修改规则只需编辑 `shared/cards.js`，然后运行：

```bash
node tools/sync-cards.js
```

### 2. 在现有 PG 环境建一张表（免费，只需一次）

云函数使用 `@cloudbase/node-sdk` 的 PostgreSQL 接口（`app.rdb()` + PostgREST），不再依赖微信云开发的文档数据库。

打开腾讯云 CloudBase 控制台 → 进入环境 `truth-unsettled-d5fu693h4e728350` → 左侧「数据库」→「SQL 编辑器」，执行：

```sql
CREATE TABLE IF NOT EXISTS public.truth_rooms (
  code        text PRIMARY KEY,
  data        jsonb NOT NULL,
  rev         integer NOT NULL DEFAULT 1,
  updated_at  bigint NOT NULL
);

GRANT ALL ON TABLE public.truth_rooms TO PUBLIC;
```

`GRANT` 是必须的：云函数使用的数据库角色默认没有新表的权限，不授权会报 `permission denied for table truth_rooms`。如果 SQL 编辑器提示“Supabase 内置角色”，点「仍然执行原始 SQL」；这里用的是 PostgreSQL 的 `PUBLIC`，不是 Supabase 角色。

执行成功即可，不需要新建环境、不需要开通付费套餐。

> 为什么不用 `wx-server-sdk`：它是微信云开发专用的，在这个腾讯云 PG 环境里访问文档数据库会报 `resource is not found`。`@cloudbase/node-sdk` 会在普通事件云函数里自动读取当前环境的临时密钥，无需手填 SecretId/SecretKey。

## 五、规则速查

### 人数配置

| 玩家数 | 建构派 | 怀疑派 | 游士 | 议题数 | 每轮摸牌 |
| :--: | :--: | :--: | :--: | :--: | :--: |
| 4 | 2 | 1 | 1 | 3 | 1 |
| 5 | 3 | 1 | 1 | 3 | 1 |
| 6 | 3 | 2 | 1 | 5 | 2 |
| 7 | 4 | 2 | 1 | 5 | 2 |
| 8 | 4 | 3 | 1 | 5 | 2 |

起始手牌摸至“心智 + 1”上限（通常 3 或 4 张）；洛克「白板」额外摸 1 张，但仍受上限限制。装备固定一攻一守两栏：第一件直接装备，同栏第二件替换旧装备。

### 胜利条件

- **建构派**：至少 1 个议题通过，且“通过”不少于“否决”（悬置不计入比较）；或淘汰全部怀疑派；
- **怀疑派**：“否决”多于“通过”，或全悬置，或存活怀疑派人数严格多于其他所有存活玩家之和；
- **游士**：完成自己的秘密契约，可与任意阵营同时获胜；死亡契约在出局后仍可获胜。

### 每轮流程

1. **夜间**：公开议题；怀疑派秘密选择一名非怀疑派玩家，全员提交后按多数结算 1 点伤害，平票无伤害；
2. **行动**：每轮随机顺序，每名存活玩家行动一次，每人 120 秒；可以连续出牌，也可以提前结束；手牌数量不超过心智 + 1；响应牌在对应时机处理；
   每回合同名主牌上限为「论证 2 张、其余各 1 张」，响应（反例、让步、辩论弃牌）不计入上限；
3. **投票**：所有存活玩家秘密投赞成 / 反对 / 悬置；通过门槛为存活人数过半（向上取整），议题「多数裁决」改为三分之二；
4. **陶片放逐**：投票结算后，每名存活玩家秘密选择一名怀疑对象，各产生一枚陶片；随机抽出一枚，被抽中者失去 1 点心智，结果公开但票向不公开；
5. **结算**：公布总票与结果，处理议题效果、契约进度与胜负；20 秒后自动进入下一轮，任何玩家也可以立即开始。

### 计时与托管

| 阶段 | 时限 | 超时处理 |
| :-- | :--: | :-- |
| 夜间 | 60s | 按已提交目标结算，未提交视为放弃 |
| 每人行动 | 120s | 自动结束该玩家回合 |
| 陶片放逐 | 30s | 未提交者由系统随机补一枚陶片 |
| 响应 | 30s | 按牌面默认选项结算（如承受诘问、辩论认输） |
| 投票 | 60s | 未提交者按悬置 |
| 本轮结算 | 20s | 自动进入下一轮 |

## 六、开发说明

### 规则数据

`shared/cards.js` 是唯一数据源，包含：

- `philosophers`：25 位角色、心智上限与两条技能文案；
- `basics` / `tricks` / `equipment`：牌名、张数、效果、目标与选择要求（`target`、`stance`、`mark`、`slot`、`reveal`、`prediction`、`responseOnly`）；
- `agendas`：10 张议题；
- `contracts`：10 张游士契约；
- `factionsByCount` / `rules`：人数配置与计时。

改完运行 `node tools/sync-cards.js`，再重新部署云函数。

### 规则引擎

云函数里的 `rules/` 不依赖 `wx-server-sdk`，可以在 Node 中直接跑：

```js
const engine = require('./cloudfunctions/game/rules/engine');
const view = require('./cloudfunctions/game/rules/view');

const room = engine.createRoom('ABC123', 4);
engine.joinRoom(room, 'openid-1', '玩家1');
// ...
engine.dispatch(room, player, 'start', {}, Date.now());
```

随机数状态保存在房间的 `rngState` 中；相同种子可以复现同一副牌与同一局判定，方便回归测试。

### 隐藏信息

`rules/view.js` 负责裁剪：

- 角色始终公开；
- 阵营只在出局或终局公开；
- 游士契约只在终局公开；
- 手牌、票向、怀疑派的夜间目标只下发给本人；
- 公开视图不含任何人的 `hand` 字段；
- 响应选项只下发给当前应回应的玩家。

`tools/simulate.js` 每一局都会遍历所有存活玩家的视角，检查阵营、契约与手牌没有泄漏。

### 云端并发

`index.js` 把房间 JSON 存进 CloudBase PostgreSQL 的 `truth_rooms` 表，并用 `rev` 乐观锁写回：

- 出牌、响应、技能、投票、开局、下一轮都在“读取 → 执行引擎 → CAS 写回”中完成；
- 冲突会重新读取并重试最多 5 次；
- 客户端重试带 `opId`，服务端按 `recentOps` 去重，避免重复出牌/投票；
- 云函数以 OpenID 识别玩家，客户端不能指定别人的身份。

## 七、已知问题与后续方向

1. **平衡尚未经过真人实测。** 当前随机模拟中“悬置”比例偏高；胜负已改为看结果分布，不再累计“通过/否决进度”。可调整的旋钮在 `shared/cards.js` 的 `rules`、议题门槛与分布胜负条件里。
2. **单人演练已支持 1 名真人 + 3 个 AI；好友局支持 2 名真人 + 2 个 AI 补位。** 4 名真人仍然体验最好。
3. **没有内置语音或文字聊天。** 联机时建议同时开语音；否则阵营协作只能依赖公开的论证标记与投票，建构派会明显更难。
4. **没有动画、音效、卡牌插画。** 当前是纸感排版 + 符号卡面。
5. **部分角色技能做了主动化简化**（见第一节差异表），如果要做完整裁判级实现，需要引入“效果中断栈”。
6. **云开发环境类型必须确认。** 若环境是 PostgreSQL-only，需要换文档型环境。
7. **房间不会主动删除玩家。** 玩家掉线后座位保留，可以用同一微信重新进入；等待阶段可以主动退出释放座位。已结束房间 6 小时后在新建房时机会式清理。
